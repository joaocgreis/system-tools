QAC / date tools

One calendar day.
Three characters.

cdate encodes dates from 2000 through 2061. ddate decodes them and uses your installed date command to format the result. This offline guide explains the validation and time-zone choices behind both commands.

Try the encoding

A1B
2010-01-11 encodes as A1B.
A1B decodes as 2010-01-11.

Year index 10 gives A. Month 1 gives 1. Day 11 gives B. Uppercase A and lowercase a describe different years.

This calculator simulates the calendar encoding only. It does not run a command, parse timestamps, access files, or make network requests.

Step 1 / encoding

The alphabet defines the range

Each position stores its own field using 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz. The year index is the year minus 2000; months and days use their ordinary numbers. With 62 year characters, the final year is 2061.

The minimum code is 011 and the maximum is zCV. Years outside the range cause an error. The year never wraps into an earlier century.
Step 2 / arguments

Parse every argument and reject conflicts

Node's parseArgs from node:util recognizes options and positional words. Strict mode rejects unknown flags. Tokens preserve duplicate occurrences, including aliases such as -u and --utc. A separate validation step rejects contradictory time-zone or formatting options.

-h and --help return before operational file access, subprocesses, and log creation. The terminal below includes the actual authored help text for both commands.

-d means debug. Use the long-only --date option to supply an input. For ddate, attach optional ISO precision as -Iseconds or --iso-8601=seconds.
Step 3 / input and files

Reject impossible calendar fields

Numeric dates are checked before the system parser sees them. Leap-year rules determine the month length, so February 30 cannot silently become a March date. Named English dates and relative expressions go through the installed parser. JavaScript parsing is opt-in and follows independent validation.

cdate --reference FILE reads only file metadata and encodes its modification date. The commands have no credentials or HTTP contract. No API fields, provider limits, authorization headers, or cookies are collected.

When both fields can be months, automatic year-last numeric input uses month/day order. Select -i dmy or -i mdy when the order matters.
Step 4 / system parser

Select a calendar day in the requested zone

Local time follows the system and TZ. -u selects UTC; -z accepts a named IANA zone. An explicit input offset identifies an instant, which is converted to the selected zone before encoding. Subprocess arguments go directly to date, without shell interpolation.

2010-01-11T00:30:00Z is January 10 in Los Angeles. An unzoned date-only input stays on January 11. With -i javascript, ISO date-only input instead follows Date.parse's UTC interpretation.

Each subprocess has a five-second timeout. Unzoned absolute clock input must round-trip without an adjustment, which catches missing local times during a DST change.

Step 5 / decoding

Three valid characters must also make a valid date

ddate checks the code's length and alphabet, then validates month and day indexes. It applies the same Gregorian leap-year rule. A year character can be lowercase, but month and day indexes never reach the lowercase part of the alphabet.

A2T is invalid because 2010 was not a leap year. C2T is valid and decodes to 2012-02-29.
Step 6 / output

Format the decoded date at midnight

The code contains no time or original zone. ddate assigns midnight in the selected zone, verifies that it exists, then delegates formatting to date. This preserves percent directives, padding and locale modifiers, ISO output, and RFC output available in your installed command.

Use ./ddate A1B +%F for a stable calendar result. Time fields describe midnight; %s describes that midnight's epoch instant. A skipped local day fails rather than shifting to another day.

Normal stdout contains only the primary result. Errors and the log-path announcement use stderr. Every standard-stream write is awaited through its write callback.

Step 7 / failures and debug

Keep diagnostics in a private log

-d or --debug creates _YYYYMMDD_HHMMSS_SCRIPTNAME.log in the current directory, using local time and the executable basename. Exclusive creation and mode 0600 protect an existing log from replacement and restrict its permissions.

The log records the plan, steps, findings, reasons for subsequent actions, validation, completion, and failures with causes. These tools perform no HTTP requests. Logs contain supplied date strings, paths, or formatting expressions and should be handled as private data.

Invalid input and unexpected errors exit with status 1. A failure while recording another failure is reported too. A late log or output failure can follow a printed result, so callers must check exit status.
Step 8 / runtime and verification

Run the executable and check the TypeScript separately

The extensionless files start with a shell/TypeScript bootstrap. The shell redirects the same source file to Node's stdin, forwards "$@", and replaces itself using exec. STANDALONE_SCRIPT_NAME preserves the real command name. The remaining comments document maintainer requirements.

Node.js 22.18+ strips erasable TypeScript syntax using --input-type=module-typescript. Runtime execution does not typecheck. The skill's bundled checker uses a private temporary .ts copy because the compiler requires a recognized suffix. Both commands must pass that strict check after edits.

The behavior suite checks all 22,646 valid calendar days and all 238,328 three-character codes, plus parser, formatting, zone, error, help, reference, and logging paths. ShellCheck applies to an extracted shell bootstrap, while the complete file is checked as TypeScript.
